# 方法契约表（冻结）

> **这是唯一的接口契约**：方法名 + 位置参数。UI 的 60+ 个调用点、CLI、以及后续各 service
> 模块全部依赖它。**方法名一个字母都不能改**（大小写敏感），参数顺序不能变，只能在末尾追加
> 可选参数（并且要同步改本表）。
>
> 数据来源：`git show c8a3813:core/...`（旧 Go 内核，已删）。旧内核用反射把
> `core/app` 的 12 个服务 + 6 个模块暴露成 156 个方法，本表即其完整清单，
> 并标注了 Flutter 应用侧（`legado-flutter/app`）的真实调用点。

## 一、使用约定

| 项 | 约定 |
| --- | --- |
| 方法名 | `<域>.<方法>`，第一段是域（`MethodDef.domain` 按第一个 `.` 切分） |
| 参数 | **位置参数**，无命名参数。Dart 侧 `handler(args)` 直接按 `args[0]`、`args[1]` 取 |
| 少传参数 | JSON 里缺项 / `null` 一律视为「未传」，保持零值（`0` / `""` / `false` / 空数组）。**所以空串与 0 常常有特殊语义**，见各行备注 |
| 多传参数 | 忽略，不报错（Go 侧 `i >= len(args)` 直接跳过） |
| 参数类型写法 | `[类型 名称]`，类型用 Dart 视角写法（`int` / `String` / `bool` / `double` / `List<int>` / `Map<String,String>`） |
| 返回 | DTO 名 + 关键字段（`[]` 表示数组，`?` 表示可能为 `null`）。完整字段见附录 A |
| 错误 | 不返回错误对象，**抛异常**。`LegadoException(code, message)`，code ∈ `NOT_FOUND` / `INVALID_ARGUMENT` / `INTERNAL` / `NOT_CONFIGURED` |
| `[]byte` 参数 | **必须 base64 编码后当 `String` 传**（JSON 不支持裸二进制）。`Source.Import`、`ReplaceRule.Import` 两个方法踩过坑 |
| 时间 | RFC3339 字符串；可空时间用 `null` |
| 枚举 | 用字符串或整数原样传，不建 Dart enum（书源 JSON 里就是这些值） |

## 二、注册顺序

旧内核 `core/modules/registry/registry.go` 的装配顺序（本表按此顺序，域内保持 Go 源文件里的声明顺序）：

```
legacy: Source → SourceDebug → SourceLogin → Shelf → Library → Reader
        → Cache → Audio → Ai → Dict → WebDAV → ReplaceRule → System
modules: Rss → Tts → Bookmark(+Record) → Settings
```

**合计 156 个方法 / 18 个方法名前缀**（规划文档里的「17 域」把 `Bookmark` 与 `Record` 算作一个模块）。

## 附录 B：最容易实现错的 5 个契约点

1. **`[]byte` 参数没有 base64 就是错的**。`Source.Import`、`ReplaceRule.Import` 的 data 在 JSON 里
   是 base64 字符串（`Source.Export`/`ReplaceRule.Export` 的返回值也是 base64）。UI 已按
   `base64Encode(utf8.encode(text))` 编码，Dart 内核必须 `base64Decode`，否则报「非法字符」。
2. **`Source.Validate` 的第二个参数是结构体对象，键是 PascalCase**：`{Search,Info,TOC,Content,Keyword}`。
   写成 `{search, info, toc, content, keyword}` 在 Go 侧能过（json 大小写不敏感），但 Dart 侧若是
   严格 map 取值会静默变成全 `false` → 只做本地静态校验，用户以为「校验通过了」。
3. **`ChapterIndex=-1` 是「没有进度」的哨兵值**，不是 0。`Reader.GetProgress`/`Shelf.GetProgress`
   无记录时必须返回 `-1`，返回 `0` 会让阅读器每次都跳到第一章。
4. **`Rss.Article.List` 是 `(sourceId, onlyUnread, offset, limit)`**，`offset` 在 `limit` 前
   （与 `Record.List(offset, limit)` 同序、与几乎所有分页接口相反）。写成 `(limit, offset)`
   在参数都小的时候看不出来，翻到第 2 页才会发现 `offset=20, limit=0` → 永远空页。
5. **`Tts.Segment` 的 `start`/`end` 是「段落内」的 rune 偏移（左闭右开），不是整章 offset**。
   两个坑叠在一起：① 用 `String.length`（UTF-16 码元）算会与 rune 数不一致（emoji/生僻字）；
   ② 把 `start` 当整章下标用，高亮会跑到文首。BMP 内的中文两者数值相同，所以这个错误
   只在漫画式排版或带 emoji 的正文里暴露，测不出来很容易带上线。

### 另外 3 个「不致命但会返工」的点

- `Source.Save` 是 **8 个扁平位置参数**，顺序 `(id,name,group,url,comment,raw,enabled,order)`；`Rss.Source.Save`
  却是 **1 个对象**。两个 Save 风格不同，别统一。
- `Source.List` **不带 `raw`**（`NewSourceBriefViews` 精简视图），`Source.Get` 才带。列表页要靠
  `SourceView.raw` 判断字段的写法一定会拿到空串；需要原始 JSON 就逐条 `Get`。
  这不是「优化」，是契约的一部分：上千书源时 `raw` 会把响应撑到几十 MB。
- `Cache.Start` 的 `scope` 是小写字符串 `all`/`remaining`/`missing`/`chapters`，不是枚举下标。
